# Трассировка требований: исследование предметной области + кейс «Альфа Хак» → реализация

Документ связывает функции и задачи из исследования предметной области, постановку задачи из кейса
и фактическую реализацию в коде. Используется жюри и командой для проверки целостности решения.

## 1. Постановка задачи (PDF, стр. 6–7)

| Требование кейса | Где реализовано |
|---|---|
| Личный кабинет клиента: выбор продукта и полный цикл от заявки до результата | `app/dashboard/page.tsx`, `app/apply/page.tsx`, `app/applications/[id]/page.tsx` |
| Этапы обработки обращений банком (движение заявки + модель решения) | `lib/pipeline.ts` (конвейер: VERIFICATION → DATA_ENRICHMENT → SCORING → решение), `lib/stateMachine.ts`, `docs/STATE_DIAGRAM.md` |
| Модель кредитного процесса: границы, этапы, участники, данные, результаты | `docs/ARCHITECTURE.md`, `prisma/schema.prisma`, `lib/status.ts` |
| Единая работающая бизнес-логика: данные сохраняются, система реагирует, состояние отображается динамически | Черновики (`DRAFT`), аудит-лог `Event`, polling 2–5 сек на клиенте, `StatusBadge` с пульсом, `Timeline` |

## 2. Минимальный сквозной кредитный путь (PDF, стр. 13–15)

| Элемент пути | Реализация |
|---|---|
| Клиент определяет цель, сумму, срок; банк получает параметры запроса | Шаг 1–2 мастера заявки (`app/apply/page.tsx`): выбор цели из списка → автоподбор продукта (маппинг `PURPOSES → product.code`) |
| Проверка полноты/корректности, уточнение информации при недостатке | `VERIFICATION` → `ADDITIONAL_INFO_REQUIRED` (`lib/pipeline.ts`), клиент уточняет параметры на карточке заявки (`/update` + повторный `/submit`) |
| Обогащение из внешних источников: БКИ, ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес» | `lib/mocks.ts` (`mockBki`, `mockEgrul`, `mockFns`), этап `DATA_ENRICHMENT`, события типа `CHECK` в таймлайне |
| Скоринг ≠ решение: оценка риска + кредитная логика (продукт, сумма, срок, проверки) | `lib/scoring.ts` (балл 0–1000 с объяснимыми факторами) + матрица решений в `lib/pipeline.ts`: ≥750 одобрение, 700–749 с условиями (сумма ×0.7), 550–699 ручной разбор, <550 отказ, стоп-фактор — недействующая компания |
| Небинарный итог: одобрение / условия / уточнение / отказ | Статусы `APPROVED`, `APPROVED_WITH_CONDITIONS`, `ADDITIONAL_INFO_REQUIRED`, `REJECTED`; ручной override кредитным специалистом в `app/backoffice/page.tsx` |
| Оформление документов и выдача (моделируются) | `acceptDecision()` в `lib/pipeline.ts`: `DOCUMENTATION → DISBURSEMENT → CLOSED` |

## 3. Исследование предметной области (разд. 1–6)

| Вывод исследования | Реализация |
|---|---|
| Проблема: сложность и длительность, непрозрачность статуса | Трекер статуса в реальном времени: `Timeline`, обновление каждые 2 сек, итоговые статусы без «чёрного ящика» |
| Проблема: информационная асимметрия, тонкие профили | Автопроверка по ИНН без документов (ЕГРЮЛ/ФНС/БКИ/ГИР БО), альтернативный скоринг по финансовой отчётности вместо залога |
| Потребность: понятные альтернативы вместо отказа | При `REJECTED` карточка заявки показывает до 2 альтернативных продуктов (`app/applications/[id]/page.tsx`) |
| Потребность: прозрачность факторов | Факторы скоринга с весами отображаются клиенту в карточке заявки (парсинг `Event.meta.factors`) |
| Потребность: скорость | Автоматический конвейер без участия оператора на типовых кейсах (~8–10 сек до решения) |
| Модель данных заявки из исследования | `Application` (status enum, scoring_result, decision) ↔ `prisma/schema.prisma`; статусная модель расширена этапами `DOCUMENTATION/DISBURSEMENT` из диаграммы состояний кейса |
| UX: оценка без кредитного следа, пошаговость, единый канал | Мастер заявки 4 шага с автосохранением черновика, демо-ИНН для мгновенной проверки |

## 4. Ограничения кейса (PDF, стр. 10–11)

| Ограничение | Соблюдение |
|---|---|
| Cloud-native, Docker, lock-файлы | `docker-compose.yml` (PostgreSQL + app), `package-lock.json`, единый вход `docker-entrypoint.sh` |
| Независимость от платных API | Все внешние источники — детерминированные моки (`lib/mocks.ts`); YandexGPT опционален, при отсутствии ключа работает офлайн-ассистент |
| Автономность от систем Альфа-Банка | Полностью автономное приложение, интеграции воспроизведены локально |
| Синтетические данные | `prisma/seed.js`, импорт ГИР БО XML (`scripts/import-fns-xml.js`), генерация компаний по хешу ИНН |
| Веб-интерфейс, процесс внутри продукта | Next.js 14 App Router, уведомления — только внутри кабинета (таймлайн + статусы) |
| Open-source LLM при использовании ИИ | YandexGPT (опционально) + прозрачный офлайн-fallback без внешних вызовов |

## 5. Критерии успеха (PDF, стр. 9)

- **Целостность** — сквозной путь «каталог → заявка → конвейер → решение → выдача» в одном продукте.
- **Готовность к проверке** — демо-аккаунты `client@demo.ru` / `operator@demo.ru` (пароль `demo123`), README со сценарием.
- **Качество UX** — трекер, факторы скоринга, альтернативы при отказе, ИИ-ассистент с контекстом заявки.
- **Согласованность** — единая статусная модель, события аудита, связность данных (User → Application → Company/Product/Event).
- **Enterprise-зрелость** — scrypt-хеширование паролей, HMAC-сессии, httpOnly-cookie, параметризованные запросы (Prisma), изоляция конвейера от HTTP, fallback ИИ.
- **Потенциал** — точки роста описаны в `docs/ARCHITECTURE.md` (очереди, репликация, кэш).
